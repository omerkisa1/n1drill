# Crash prediction — n1-worker-2

Written before power-cycling `n1-worker-2` from the hypervisor (0B.041).
Do not edit this file after the crash runs — add the real outcome to
`07-crash-actual.md` instead and compare.

This is a **hard** failure, not a drain. There is no `kubectl drain` asking
anything nicely first — the kubelet just stops reporting. Everything here
follows from that one fact.

## The core difference from the drain experiment

`kubectl drain` is a voluntary disruption: the API server evicts pods one
by one and respects PodDisruptionBudgets, `nodeName` ownership rules, and
`--ignore-daemonsets`. A crashed node produces an **involuntary**
disruption instead — the control plane doesn't ask, it just eventually
decides the node is gone and deletes whatever was on it.

That difference predicts three concrete reversals of the drain results:

1. **PDBs will not apply.** `django-app`'s `minAvailable: 3` PDB blocked
   eviction during the drain. It has no say here — PDBs only guard
   voluntary evictions initiated through the eviction API. If a
   `django-app` replica is on `n1-worker-2`, it gets deleted and
   rescheduled like anything else, PDB or not.
2. **The DaemonSet pod will die.** `--ignore-daemonsets` isn't a thing
   when there's no `drain` command running. `node-agent`'s pod on
   `n1-worker-2` goes down with the node and won't resurrect until the
   node itself comes back (DaemonSet pods aren't rescheduled elsewhere —
   there's one per node by design).
3. **`bare-pod` and `pinned-pod` are permanently lost**, not just
   blocked. During the drain, `pinned-pod` (no owner, `nodeName` pinned)
   stopped the drain from completing. Here there's no drain to stop —
   if either pod is on `n1-worker-2`, it has no controller to recreate it
   and no running node to live on. It is gone until someone notices and
   creates it again by hand.

## The timing question

Node state goes `Ready` → `NotReady` almost immediately (missed
heartbeats), but pods on it don't get evicted right away. The default
`node.kubernetes.io/not-ready` and `node.kubernetes.io/unreachable`
toleration window (`tolerationSeconds`) is **300 seconds**. Expect pods
with controllers to sit in `Running` (stale) state for up to ~5 minutes
before the node controller marks them for deletion and the scheduler
places replacements elsewhere. This wait is the headline number for this
experiment.

## Expected to reschedule after the ~300s wait

- `no-requests-app` replicas on this node — no PDB, no affinity, should
  land on `n1-worker-1`/`n1-worker-3` once evicted.
- `django-app` replicas on this node — PDB is irrelevant here, see above.
- `jenkins-0`, if its PV wasn't pinned to this node via `nodeAffinity`;
  stuck `Pending` with a volume conflict otherwise, same as the drain
  case, since `local-path` volumes can't follow a pod across nodes.

## Expected to be unaffected

- `crowded-app` — only schedulable on `n1-worker-1` anyway.
- `fragmentation-probe`, `unschedulable-selector` — already `Pending`
  before the crash, unrelated to this node.
- `db-pod` — only unaffected if it isn't actually placed on
  `n1-worker-2`.

## What recovery should look like

Once the VM is powered back on, `n1-worker-2` should rejoin as `Ready`
within a couple of minutes (RKE2 agent restarts automatically). Anything
that got rescheduled elsewhere stays there — Kubernetes doesn't move pods
back to a recovered node. Only `node-agent`'s DaemonSet pod should come
back on `n1-worker-2` itself, since a new one gets scheduled there the
moment the node is `Ready` again.
